# HMGD Phase 2 — Opt-in GAIAN Practice Profile

Status: **listed**  
Issues: #531 / #158 / #164  
Crate already on `main`: `gaia-hmgd::{HmgdProfile, infer_belief, mine_denomination}`.

---

## What exists on main

- `HmgdProfile::new()` — empty `declared` vec, `piety_score == None`.
- `gaian_works_empty()` returns `true` on an empty profile. GAIAN is fully functional with no practices declared.
- `infer_belief(profile)` / `mine_denomination(profile)` → `BeliefInferred` (read-only inference, never written back as a score).
- `prohibited()` already names child-ordeal practices; no new prohibitions added here.

---

## Surface rules (MUST)

```
profile_is_opt_in()          → true   // no profile created without explicit user action
chat_mined_for_denomination() → false  // chat history MUST NOT feed infer_belief
mandatory_piety_score()      → false  // piety_score field MUST remain None unless user sets it
ritual_as_treatment()        → false  // no practice node may carry a treatment claim
child_profile_guardian_gate() → GuardianApproved | Refused  // child entries require guardian approval
```

Any code path that sets `piety_score` from chat context MUST be refused at compile time via a
`#[forbid(...)]` lint or a `MandatoryPietyError` return.

---

## Practice log rules

- User declares practices, traditions, and tools explicitly — no inference from chat.
- Each declared entry carries: `realm` (from `realms.csv`), `tradition` (free text, max 128 chars),
  `tool` (optional free text), `since` (optional year).
- An entry with no `realm` is refused: `Err(MissingRealm)`.
- Duplicate entries (same realm + tradition) are deduplicated silently.

---

## Optional reminders

- Reminders are user-enabled per entry. Default: off.
- `reminder_enabled(entry_id)` MUST return `false` until the user explicitly toggles it.
- Reminder text is user-authored; GAIA MUST NOT auto-generate ritual language.
- Reminders are stored locally; they MUST NOT be transmitted to any upstream without explicit
  GAIAN export consent (see issue #65 / `gaia-gaian`).

---

## Health-adjunct screen

- When a practice is logged near a symptom context, GAIA MUST display:
  `"This is an adjunct resource, not a medical treatment."`
- This screen is informational only; it MUST NOT block practice logging.
- `health_adjunct_disclaimer_shown(context)` MUST return `true` whenever a symptom keyword
  is present in the same session as a practice log action.
- No practice node may carry a diagnosis, treatment, or cure claim.
  Violation: `Err(TreatmentClaim)`.

---

## Child profile gate

- A minor GAIAN's practice profile MUST be empty until a guardian approves entries.
- `child_profile_guardian_gate(entry)` → `GuardianApproved` | `Refused`.
- Entries refused by the gate MUST NOT appear in the declared list.
- Guardian approval is per-entry, not per-session.

---

## Export and deletion

- Full profile export and deletion are governed by `gaia-gaian` issue #65.
- This phase adds no new export surfaces; it only declares that the practice log
  is subject to the existing export/delete contract.
- `profile_exportable()` → `true` (export is always available).
- `profile_deletable()` → `true` (deletion is always available; clears all declared entries
  and resets `piety_score` to `None`).

---

## Refuse (compile-time or runtime)

- Religiosity score inferred from chat → `Err(ChatMinedDenomination)`
- Mandatory piety gate blocking GAIAN → `Err(MandatoryPiety)`
- Ritual logged as a treatment → `Err(TreatmentClaim)`
- Child entry without guardian gate → `Err(GuardianRequired)`
- Practice entry with no realm → `Err(MissingRealm)`
- Reminder auto-text generated by GAIA → `Err(AutoRitual)`

---

## What is not here

- Live interfaith reconciliation engine — not on main, not in scope for this phase.
- Shared collective practice rooms — that is Phase 3 (#165), already listed.
- Belief-scoring UI — no score is ever displayed to the user from this profile.
- Server-side practice sync — local only until `gaia-gaian` export consent is given.
